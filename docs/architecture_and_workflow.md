# 商业激活系统：核心架构、工作流与使用指南 (Architecture & Workflow)

本文档全面阐述了本商业激活系统的开发思想、核心工作流以及实际使用方法。旨在帮助您或未来的二次开发人员快速理解项目全貌。

---

## 1. 💡 核心开发思想 (Philosophy)

本系统在设计与开发过程中，始终贯彻以下三大核心原则：

### 1.1 绝对安全优先 (Security First)
作为一款商业激活系统，防破解是生命线。
- **零明文存储**：数据库中绝对不保存激活码明文。无论黑客通过何种手段拖取了数据库，看到的只能是一堆无规律的 SHA256 乱码。
- **信息黑洞防嗅探**：无论是激活失败、机器码错误还是额度用尽，前端统一只显示极简的“授权失败”提示。坚决不向攻击者暴露系统内部的判定逻辑和错误原因，彻底堵死暴力撞库的可能。

### 1.2 极简与轻量化 (Extreme Lightweight)
系统将要部署在可能资源有限的服务器上，因此我们在架构上做了极限瘦身：
- **摒弃重度前端运行时**：前端抛弃了需要长期吃内存的 Node.js，采用静态导出 (`output: export`) 的方式，最终仅仅是一堆 HTML/JS/CSS 文件，由轻量级的 Nginx 极速托管。
- **后端的 Alpine 化**：C# 后端剥离了一切不必要的环境组件，采用体积极小的 `.NET Alpine` 运行时，大大降低了 CPU 和内存的损耗。

### 1.3 容器化黑盒网络 (Containerized Blackbox)
- **内外网硬隔离**：后端应用 (5000) 和 数据库 (5432) 全部藏在 Docker 内部的虚拟局域网中，**绝对不对宿主机公网开放端口**。
- **唯一入口**：整个系统只通过 Nginx 的 80/443 端口对外沟通，所有到达后端的请求必须经过 Nginx 反向代理层层过滤。

## 2. 🔄 核心工作流程 (Workflow)

系统的业务逻辑基于 **B2B2C** 商业模式，主要分为“管理员后台发卡”与“C端客户离线激活”两条主线：

### 2.1 颁发激活码流程 (Admin Flow)
1. 客户付款后，系统管理员或自动发卡机器人调用 `POST /api/admin/generate-license`。
2. 后端生成一个极度随机的 32 位激活码字符串（明文）。
3. 后端系统对这个明文进行 **SHA256 不可逆哈希运算**。
4. **数据库只保存哈希值**。
5. 后端将原始明文激活码返回给管理员，管理员交由第三方渠道销售给客户。（一旦错过，连系统管理员也无法再次看到该激活码的明文）。

### 2.2 客户端自动激活与换机流程 (Client Activation Flow)
1. 终端用户的客户端软件收集用户硬件指纹（如 CPU ID + 主板序列号），只需与用户输入的**激活码明文**打包，**无需提供任何邮箱或注册信息**。
2. 客户端向服务器发起 `POST /api/license/activate` 请求。
3. 服务器收到明文激活码后，再次进行 SHA256 运算，得出哈希值，并在数据库内精确匹配。
4. **比对与风控判定**：
   - 检查该激活码的过期时间与挂起状态。
   - 检查该硬件指纹是否已记录在案。
   - 若是新硬件指纹，则检查该激活码关联的当前设备数量是否超过 `MaxDevices`。
   - **智能换机 (Auto-Revoke)**：若设备数量已满，且激活码剩余允许的换机次数 (`MaxActivations`) > 0，系统将**自动吊销绑定时间最老的旧设备**，并绑定当前新设备。
5. **返回离线签名**：激活成功后，后端使用 2048 位私钥签发一串 Base64 签名串返回给客户端。客户端使用内嵌的公钥验证签名的合法性。

## 3. 🛠️ API 使用方法与测试指南 (Usage)

由于本地开发电脑并未安装 PostgreSQL 数据库，**系统的级联测试需通过 Docker (`docker-compose.lan.yml` 或 `docker-compose.yml`) 启动后进行。**

### 3.1 批量生成激活码 (管理员接口)
- **请求方式**: `POST`
- **URL**: `http://<您的服务器IP>/api/admin/generate-license`
- **请求头**: 需携带 Cookie Session (通过后台登录获得)
- **请求体 (JSON)**:
  ```json
  {
    "count": 10,
    "maxDevices": 1,
    "maxActivations": 3,
    "licenseType": "Permanent",
    "expirationDate": null
  }
  ```
- **测试结果预期**: 返回一个包含 10 个纯文本形式明文激活码的 JSON 数组。

### 3.2 模拟客户端激活 (终端开放接口)
- **请求方式**: `POST`
- **URL**: `http://<您的服务器IP>/api/license/activate`
- **请求体 (JSON)**:
  ```json
  {
    "licenseKey": "XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX",
    "hardwareId": "HW-CPU-12345678"
  }
  ```
- **测试结果预期**: 第一次请求应返回激活成功与离线 RSA 签名信息。如果尝试用不同的 `hardwareId` 激活，且超出了允许换机的次数，则返回“授权失败”。

### 3.3 吊销指定硬件设备 (管理员接口)
- **功能描述**: 手工强制解绑某个指定硬件设备的权限。
- **请求方式**: `DELETE`
- **URL**: `http://<您的服务器IP>/api/admin/devices/{deviceId}`
- **说明**: B2B2C 模式下，因具备“智能换机”机制，通常不需要管理员手动吊销设备，该接口作为风控后门保留。
