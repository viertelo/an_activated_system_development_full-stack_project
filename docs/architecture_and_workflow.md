# 商业激活系统：核心架构、工作流与使用指南 (Architecture & Workflow)

本文档全面阐述了本商业激活系统的开发思想、核心工作流以及实际使用方法。旨在帮助您或未来的二次开发人员快速理解项目全貌。

---

## 1. 💡 核心开发思想 (Philosophy)

本系统在设计与开发过程中，始终贯彻以下三大核心原则：

### 1.1 绝对安全优先 (Security First)
作为一款商业激活系统，防破解是生命线。
- **零明文存储**：数据库中绝对不保存激活码明文。无论黑客通过何种手段拖取了数据库，看到的只能是一堆无规律的 SHA256 乱码。
- **信息黑洞防嗅探**：无论是激活失败、机器码错误还是额度用尽，前端统一只显示极简的“授权失败”提示。坚决不向攻击者暴露系统内部的判定逻辑和错误原因，彻底堵死暴力撞库的可能。

### 1.2 极简与轻量化 (Extreme Lightweight)
系统将要部署在可能资源有限的服务器上，因此我们在架构上做了极限瘦身：
- **摒弃重度前端运行时**：前端抛弃了需要长期吃内存的 Node.js，采用静态导出 (`output: export`) 的方式，最终仅仅是一堆 HTML/JS/CSS 文件，由轻量级的 Nginx 极速托管。
- **后端的 Alpine 化**：C# 后端剥离了一切不必要的环境组件，采用体积极小的 `.NET Alpine` 运行时，大大降低了 CPU 和内存的损耗。

### 1.3 容器化黑盒网络 (Containerized Blackbox)
- **内外网硬隔离**：后端应用 (5000) 和 数据库 (5432) 全部藏在 Docker 内部的虚拟局域网中，**绝对不对宿主机公网开放端口**。
- **唯一入口**：整个系统只通过 Nginx 的 80/443 端口对外沟通，所有到达后端的请求必须经过 Nginx 反向代理层层过滤。

## 2. 🔄 核心工作流程 (Workflow)

系统的业务逻辑主要分为“管理员发卡”与“客户端激活”两条主线：

### 2.1 颁发激活码流程 (Admin Flow)
1. 客户付款后，调用 `POST /api/admin/generate-license`。
2. 管理员（后端）生成一个极度随机的 32 位激活码字符串（明文）。
3. 后端系统对这个明文进行 **SHA256 不可逆哈希运算**。
4. **数据库只保存哈希值**。
5. 后端将原始明文激活码返回给管理员，并发送给客户。（一旦错过，连系统管理员也无法再次看到该激活码）。

### 2.2 客户端激活流程 (Client Activation Flow)
1. 客户端软件收集用户硬件指纹（如 CPU ID + 主板序列号），与用户输入的激活码明文以及绑定的邮箱地址一起打包。
2. 客户端向服务器发起 `POST /api/license/activate` 请求，并在请求体验证邮箱与 License 的归属关系。
3. 服务器收到明文激活码后，再次进行 SHA256 运算，得出哈希值。
4. 服务器拿着这个哈希值去数据库里比对。
5. **比对成功**：
   - 检查该激活码的 `MaxDevices`（最大设备数）。
   - 如果该硬件指纹未绑定，且设备数量未满，则将该硬件记录在案，返回**激活成功**。
   - 如果硬件指纹已存在（同一台机器重装系统），直接返回**激活成功**。
   - 如果是陌生设备且额度已满，返回**激活失败**。

### 2.3 高级身份认证与重置流程 (Advanced Auth Flow)
为了适应更高安全级别的需求，我们加入了从注册到重置的全链路验证体系：
1. **邮箱强制验证**：用户在 `POST /api/auth/register` 注册后，账号处于冻结状态。系统自动向其发送带有唯一 Token 的验证邮件，点击后调用 `GET /api/auth/verify-email` 解锁账号。
2. **2FA 动态密码 (Google Authenticator)**：系统提供 `POST /api/auth/2fa/setup` 生成 TOTP 密钥和二维码。绑定后，每次登录 (`POST /api/auth/login`) 都强制要求输入手机上的 6 位动态验证码。
3. **“零暴露”找回激活码机制**：
   - 用户遗忘激活码时，发起 `POST /api/license/forgot`，系统发送确认邮件。
   - 用户点击重置链接 (`GET /api/license/reset`)，系统**不仅会颁发新的激活码，而且会强制彻底吊销 (Revoke) 名下所有正在生效的旧激活码**，并通过邮件仅将新激活码的明文发送给用户，完全堵死了旧激活码泄露后的滥用漏洞。

## 3. 🛠️ API 使用方法与测试指南 (Usage)

由于本地开发电脑（Windows）并未安装 PostgreSQL 数据库，**最终的系统级联测试需要将代码推送到 Linux 服务器并通过 Docker 启动后方可进行。**

当您的服务器运行起 `docker-compose up -d` 后，即可通过以下接口测试业务链路：

### 3.1 生成新激活码 (管理员接口)
- **请求方式**: `POST`
- **URL**: `http://<您的服务器IP>/api/admin/generate-license`
- **请求头**: 需携带 JWT Token (若开启了鉴权)
- **请求体 (JSON)**:
  ```json
  {
    "userId": "client_uuid_123",
    "maxDevices": 1,
    "count": 1,
    "licenseType": "Permanent",
    "expirationDate": "2027-01-01T00:00:00Z"
  }
  ```
- **测试结果预期**: 返回一个纯文本形式的明文激活码（例如 `LIC-A1B2...`）。

### 3.2 模拟客户端激活 (用户接口)
- **请求方式**: `POST`
- **URL**: `http://<您的服务器IP>/api/license/activate`
- **请求体 (JSON)**:
  ```json
  {
    "email": "user@example.com",
    "licenseKey": "LIC-A1B2... (刚才生成的明文)",
    "hardwareId": "HW-CPU-12345678"
  }
  ```
- **测试结果预期**: 第一次请求应返回激活成功信息。如果更换 `hardwareId` 再次请求，且额度为 1，则必定返回“授权失败”。

### 3.3 吊销指定硬件设备 (管理员接口)
- **功能描述**: 当客户更换电脑，需要解绑旧电脑时使用。
- **请求方式**: `DELETE`
- **URL**: `http://<您的服务器IP>/api/device/remove/{deviceId}`

### 3.4 人员与角色管理 (管理员接口)
- **功能描述**: 查询系统中注册的用户、更改用户角色（提权）或删除用户。
- **获取用户列表**: `GET /api/admin/users`
- **更改角色 (Admin/User)**: `PUT /api/admin/users/{id}/role` (请求体 `{"role": "Admin"}`)
- **删除用户**: `DELETE /api/admin/users/{id}`
